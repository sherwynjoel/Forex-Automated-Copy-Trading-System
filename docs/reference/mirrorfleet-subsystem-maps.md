## MirrorFleet API authentication, session, MPIN and org role model (api/src/api: auth.py, rbac.py, oauth.py, config.py, routes/mpin.py, routes/orgs.py, routes/investor.py, ws.py; db/migrations 005, 010, 019, 020, 021; dashboard/src/lib/api.ts, types.ts, roles.ts, components/PinInput.tsx)

Stateless signed-cookie sessions (itsdangerous URLSafeTimedSerializer, salt "session", 12 h) carrying {user_id, sv, pin}. Email+password (POST /api/login or /api/register) issues a HALF session (pin=False) that may only call /api/mpin/set|verify|reset, /api/logout and a trimmed GET /api/me. Passing the 6-digit MPIN re-issues the cookie with pin=True (FULL session); require_user refuses pin=False with 401 "MPIN required". users.session_version is baked into the cookie and compared on every request so password/MPIN change or logout-all revoke all cookies. Org roles live in org_memberships.role (admin > viewer > investor); routes declare their gate with Depends(require_org_role("admin"|"viewer"|"investor")) on a path containing {org_id}. Registration is closed unless REGISTRATION_ENABLED=true or a valid invite token is supplied. MPIN lockout: 5 wrong tries -> 15 min lock stored on users row.

### Contracts

- Session cookie: name "session", value = URLSafeTimedSerializer(cfg.session_secret, salt="session").dumps({"user_id": int, "sv": int, "pin": bool}); httponly=True, samesite="lax", secure=cfg.cookie_secure, max_age=SESSION_MAX_AGE_S=43200 (12 h). Companion cookie "csrf" = secrets.token_urlsafe(32), httponly=False, same attrs. Both set by auth._issue_session(response, cfg, user_id, session_version=0, *, pin).
- Session unpack: auth._unpack_session(session, cfg) -> (user_id, sv, pin) or None on BadSignature/SignatureExpired; missing 'sv' reads as 0, missing 'pin' reads as False. auth.session_identity(session, cfg) is the same for non-Depends callers (WebSocket).
- Revocation: users.session_version INTEGER NOT NULL DEFAULT 0; auth.session_version_matches(conn, user_id, version) -> bool (missing user fails closed). Bumped by POST /api/me/password, POST /api/me/logout-all, POST /api/mpin/reset, POST /api/me/mpin; each also calls ws.broadcaster.close_for_user(user_id).
- Dependency auth.require_half_session(session=Cookie(None), cfg, conn) -> SessionInfo(user_id: int, session_version: int, pin: bool); 401 "Not authenticated" when no/invalid cookie, 401 "Session expired" when session_version mismatches.
- Dependency auth.require_user(session, cfg, conn) -> int user_id; calls require_half_session then raises 401 detail "MPIN required" if info.pin is False.
- Dependency rbac.require_org_role(min_role: 'investor'|'viewer'|'admin') -> callable(org_id: int path param, user_id=Depends(require_user), conn) -> OrgContext(org_id: int, user_id: int, role: str, user_email: str=''); 404 "Not found" for non-member or nonexistent org, 403 "Insufficient role" when ROLE_RANK[role] < ROLE_RANK[min_role]. ROLE_RANK = {"investor": -1, "viewer": 0, "admin": 1}.
- rbac.require_account_in_org(conn, org_id, account_id) -> None; 404 "Account not found" unless accounts.ctid_trader_account_id = account_id AND accounts.org_id = org_id.
- POST /api/register body RegisterRequest {email: str, password: str, display_name: str, invite_token: Optional[str]=None} -> 204 + half-session cookies (pin=False). 403 when not cfg.registration_enabled and invite_token not open; 429 per-IP; 400 invalid email / password < MIN_PASSWORD_LEN=10 / empty display_name; 409 "Email already registered".
- POST /api/login body LoginRequest {email: str, password: str} -> 204 + half-session cookies (pin=False, sv=users.session_version). 401 "Invalid email or password"; 429 per-credential bucket key f"login:{email}:{client_ip}" (5/60 s) and per-source f"login-ip:{client_ip}" (20/60 s, skipped when client_ip is loopback/unknown).
- POST /api/logout -> 204, deletes cookies session and csrf (no auth required; CSRF still enforced).
- GET /api/me (require_half_session): half session -> {"mpin": {"pending": true, "set": bool}}; full session -> {"user": {"id", "email", "display_name"}, "orgs": [{"id", "name", "role"}], "mpin": {"pending": false, "set": bool}}.
- POST /api/me/password (require_user) body {current_password, new_password} -> 204, bumps session_version, re-issues cookie pin=True; 403 "Current password is incorrect", 400 length/same.
- POST /api/me/logout-all (require_user) -> 204, bumps session_version, deletes cookies.
- POST /api/mpin/set (require_half_session) body SetRequest {mpin: str, mpin_confirm: str} -> 204 + cookie re-issued with pin=True and same session_version; 400 "MPIN must be exactly 6 digits" (MPIN_RE ^[0-9]{6}$) / "MPINs do not match"; 409 "MPIN already set". Audit action 'mpin_set'.
- POST /api/mpin/verify (require_half_session) body VerifyRequest {mpin: str} -> 204 + cookie pin=True; failures from _check_mpin: 409 {"detail":"MPIN not set"}, 423 {"detail":"MPIN locked","locked_until": ISO}, 401 {"detail":"Invalid MPIN","attempts_left": int}.
- POST /api/mpin/reset (require_half_session) body ResetRequest {password: str, mpin: str, mpin_confirm: str} -> 204, stores new MPIN, bumps session_version, cookie pin=True; works while locked; shares login rate-limit buckets; 401 "Invalid password". Audit 'mpin_reset'.
- POST /api/me/mpin (require_user, full session) body ChangeRequest {current_mpin: str, mpin: str, mpin_confirm: str} -> 204, bumps session_version, cookie pin=True; same 401/423/409 failure bodies. Audit 'mpin_changed'.
- routes.mpin._check_mpin(conn, user_id, mpin: str) -> Optional[Response]: None on success (resets mpin_failed_attempts=0, mpin_locked_until=NULL); otherwise the JSONResponse to return (409 / 423 / 401 with attempts_left). Atomic UPDATE reservation: users.mpin_failed_attempts += 1 WHERE mpin_hash IS NOT NULL AND (mpin_locked_until IS NULL OR <= now()) AND mpin_failed_attempts < MPIN_MAX_ATTEMPTS=5; on the 5th failure sets mpin_locked_until = now + MPIN_LOCK_MINUTES=15 and audits 'mpin_locked'. Exactly one argon2 verify on every path.
- routes.mpin._audit(conn, user_id, action) inserts events (org_id NULL, account_id NULL, category 'auth', severity 'info', payload {action, user_id}).
- Table users: id BIGSERIAL PK, email TEXT NOT NULL (unique index on lower(email)), password_hash TEXT NOT NULL, display_name TEXT NOT NULL, created_at TIMESTAMPTZ, session_version INTEGER NOT NULL DEFAULT 0, mpin_hash TEXT, mpin_failed_attempts INTEGER NOT NULL DEFAULT 0, mpin_locked_until TIMESTAMPTZ, mpin_set_at TIMESTAMPTZ.
- Table orgs: id BIGSERIAL PK, name TEXT NOT NULL, copying_enabled BOOLEAN DEFAULT true, dry_run BOOLEAN DEFAULT false, created_at TIMESTAMPTZ.
- Table org_memberships: org_id BIGINT FK orgs ON DELETE CASCADE, user_id BIGINT FK users ON DELETE CASCADE, role TEXT CHECK (role IN ('admin','viewer','investor')), created_at, PRIMARY KEY (org_id, user_id).
- Table org_invites: id BIGSERIAL PK, org_id FK, role TEXT CHECK IN ('admin','viewer','investor'), token_hash TEXT NOT NULL UNIQUE (sha256 hex of raw token), created_by FK users, created_at, expires_at TIMESTAMPTZ NOT NULL (now()+7 days, INVITE_TTL_DAYS), consumed_at TIMESTAMPTZ, consumed_by FK users.
- accounts.investor_user_id BIGINT NULL FK users ON DELETE SET NULL; INDEX accounts_by_investor ON accounts (org_id, investor_user_id) WHERE investor_user_id IS NOT NULL (non-unique since migration 024, client portal phase 3: an investor may own several accounts, up to portal_settings.max_live_accounts, default 5; an account still has at most one owner). Investor router resolves the account with pc.pick_account(conn, org_id, user_id, account_id) -> int, which accepts an optional `account_id` from the request's query/body but 404s unless pc.owns_account(conn, org_id, user_id, account_id) says it is one of the caller's own accounts (pc.linked_accounts lists them all); omitted it falls back to the investor's only account, 409 while they have none and 400 "account_id is required" while they have several.
- POST /api/orgs body {name} (require_user) -> 201 {id, name, role:'admin'}; POST /api/orgs/join body JoinRequest {token} (require_user) -> {org_id, role}; 410 invalid/expired/used, 409 "Already a member". POST /api/orgs/{org_id}/invites body {role: 'admin'|'viewer'|'investor'} (admin) -> 201 {id, role, token, expires_at}.
- Investor portal routes (prefix /api/orgs/{org_id}, require_org_role("investor")): GET /investor/summary, GET /investor/wallet, GET/POST /investor/deposits, GET/POST /investor/withdrawals (POST body WithdrawalRequest {amount, destination}; 409 "no account linked yet"; 429 after REQUESTS_PER_HOUR=10; 400 amount exceeds available), GET /investor/positions, /investor/analytics, /investor/history/{kind}. Admin side (require_org_role("admin")): GET/PUT /investor-wallet, GET /investors, PUT /investors/{user_id}/account, GET /investor-deposits, POST /investor-deposits/{deposit_id}/decision, GET /investor-withdrawals, POST /investor-withdrawals/{withdrawal_id}/decision, POST /investor-withdrawals/{withdrawal_id}/paid.
- CSRF: CSRFMiddleware requires cookie 'csrf' == header 'x-csrf-token' on POST/PUT/DELETE/PATCH except exact paths /api/login, /api/register and prefixes CSRF_EXEMPT_PREFIXES = ('/api/webhooks/', '/api/mt5/'); 403 "Missing CSRF token" / "Invalid CSRF token".
- WebSocket: cookie 'session' via session_identity; closes 4401 unless pin=True and session_version_matches; 4400 without org_id query param; then org_memberships role lookup.
- Dashboard: api<T>(path, init?, opts?: {redirectOn401?: boolean}) in dashboard/src/lib/api.ts; ApiError.response = {status, body}. PinInput props: {id: string, label: string, value: string, onChange: (next: string) => void, onComplete?: (pin: string) => void, disabled?: boolean, error?: string | null, autoFocus?: boolean}. Role type 'investor'|'viewer'|'admin'; can(role, 'trade'|'control'|'manage_members').

### Constraints

- Every route that uses require_org_role must declare {org_id} as a PATH parameter (the dependency reads it by name); query params do not work.
- Non-membership and nonexistent orgs return 404, never 403, so org existence does not leak; the investor role ranks -1, below viewer, so every viewer-or-higher endpoint refuses investors automatically and only the investor router (require_org_role("investor")) admits them.
- Half vs full session is enforced centrally: anything depending on require_user (directly or via require_org_role) is behind the MPIN with no per-route edit. Only require_half_session routes (/api/mpin/set|verify|reset, GET /api/me) plus /api/logout are reachable with pin=False. Cookies issued before the MPIN deploy read as pin=False and must re-verify.
- MPIN lock state lives on the users row (shared across workers, survives restarts). _check_mpin reserves an attempt with a single guarded UPDATE so concurrent bursts get at most 5 verifies per window; the lock is judged by the database clock (SELECT now()), not the API clock. Reset clears the lock (that is its purpose) but is rate-limited by login's per-credential bucket.
- Every MPIN path (verify, reset, change) does exactly one argon2 verify whatever the outcome (dummy hash _DUMMY_HASH for the failure branches) so timing does not leak whether an MPIN is set or locked. Preserve this if reusing _check_mpin.
- The MPIN verify/set/reset routes re-issue the cookie with the SAME session_version (info.session_version); reset and change bump session_version and sign out every other session plus close their websockets.
- Registration: POST /api/register is refused (403) unless REGISTRATION_ENABLED is true/1/yes OR request_data.invite_token matches an unconsumed, unexpired org_invites row (auth._invite_is_open, read-only). The invite is consumed only by POST /api/orgs/join, so a token survives a failed signup. Production currently runs with registration closed (memory: prod-reset note).
- The frontend api() wrapper redirects on 401 for all paths except /api/login, /api/me/mpin and /api/mpin/*; a new endpoint that returns its own 401 (e.g. "Invalid MPIN" on a PIN-gated action) must be called with opts {redirectOn401: false} or added to that exclusion list, otherwise a wrong PIN bounces the user to /login.
- CSRF middleware exempts only /api/login, /api/register and the '/api/webhooks/' and '/api/mt5/' prefixes (trailing slash load-bearing); every other mutating call needs the X-CSRF-Token header from the 'csrf' cookie (api.ts adds it automatically).
- Audit rows: MPIN events use category 'auth' with org_id NULL; investor ledger events use category 'control' with actor_email = OrgContext.user_email and severity 'warning' for requests, 'info' for decisions.
- MIN_PASSWORD_LEN = 10; MPIN must match ^[0-9]{6}$; investor deposit/withdrawal POSTs are capped at 10 per org+user per hour by a separate LoginRateLimiter(max_attempts=10, window_s=3600).
- org_memberships PRIMARY KEY (org_id, user_id): one role per user per org; an org must keep at least one admin (409 on demotion/removal of the last one, enforced with FOR UPDATE row locks).
- ROLE_RANK is mirrored in dashboard/src/lib/roles.ts (RANK) and the DB CHECK constraints in 020_single_admin.sql; adding a role means changing all three.

### Reuse for the portal

- Session and CSRF plumbing (auth._issue_session, require_half_session, require_user, CSRFMiddleware, dashboard api()) can be used unchanged: a portal client is just a user whose org_memberships.role = 'investor'.
- Role gating: declare portal endpoints as `ctx: OrgContext = Depends(require_org_role("investor"))` under an APIRouter(prefix="/api/orgs/{org_id}"), exactly as routes/investor.py does; admin-side queues use require_org_role("admin"). ctx gives org_id, user_id, role, user_email for audit.
- Wallets / deposits / withdrawals already exist as tables (org_investor_wallets, investor_deposits, investor_withdrawals) and endpoints (GET/POST /api/orgs/{org_id}/investor/deposits and /investor/withdrawals, admin decision and paid endpoints). A multi-wallet or internal-transfer feature would need new tables; the current design is one receiving address per org and one linked account per investor (accounts.investor_user_id unique per org).
- PIN-gated action (e.g. confirm a withdrawal with the MPIN): there is no standalone re-verify endpoint today. The reusable primitive is routes.mpin._check_mpin(conn, user_id, mpin) -> Optional[Response]: call it inside the action handler (which already runs under require_user / require_org_role, i.e. a full session), validate the body field against MPIN_RE first, and if it returns a Response return that (409 MPIN not set / 423 locked with locked_until / 401 Invalid MPIN with attempts_left) before performing the action. It shares the same 5-attempt / 15-minute lock on the users row and audits 'mpin_locked'. On the dashboard, call the endpoint with api(path, init, { redirectOn401: false }) and reuse the 401/423 handling from pages/Mpin.tsx and components/AccountSecurity.tsx, with PinInput for entry. Alternatively factor _check_mpin into a Depends-style helper, but today it is a module-private function in routes/mpin.py.
- MPIN set/verify/reset/change flows and the /mpin page (Set, Verify, Forgot modes) are complete and reusable for the portal login; GET /api/me tells the client whether the MPIN is pending/set.
- KYC: nothing exists. users has only email, password_hash, display_name plus session/MPIN columns; a KYC feature needs new columns or a table and new endpoints (likely investor-side POST under /investor/... and admin-side review under require_org_role("admin")).
- Manager marketplace, tickets, notifications: nothing exists. The events table (org_id, account_id, category, severity, payload, actor_email) and ws.broadcaster (close_for_user, close_org, close_for) are the only notification-like infrastructure; investor audit events use category 'control'.
- Onboarding: invites (POST /api/orgs/{org_id}/invites with role 'investor', raw token returned once, /join/:token page, POST /api/orgs/join) plus POST /api/register with invite_token are the existing way to create investor accounts while REGISTRATION_ENABLED is false. Open self-signup would require setting REGISTRATION_ENABLED=true and a way for a new user to end up with an investor membership (today a registered user with no invite lands on /welcome with no org).
- Password and MPIN self-service (POST /api/me/password, POST /api/me/mpin, POST /api/me/logout-all) and the AccountSecurity component can be surfaced in a portal Security page as-is.

## MirrorFleet investor money model (investor portal ledger: wallet card, deposit notices, withdrawal requests, account link)

A record-only ledger: the app never holds keys or moves funds. Each org has at most one receiving wallet row (org_investor_wallets). An investor (membership role 'investor', ROLE_RANK -1, refused by every viewer+ desk endpoint) files deposit notices (pending -> confirmed|rejected by admin) and withdrawal requests (requested -> approved|rejected -> paid|rejected by admin). Money figures come from summarise(): only confirmed deposits and paid withdrawals moved; requested+approved withdrawals are 'pending_withdrawn'; available = equity - pending_withdrawn where equity is live from copier /state, else mt5_links.equity ('last known'), else null. Admin links exactly one non-master account per investor via accounts.investor_user_id. No proof/receipt upload exists; a txid string is the only evidence on both sides.

### Constraints

- Available rounding bug (known, parked in memory): summary_json returns available = float(quantize(0.01, ROUND_HALF_UP)) of the UNROUNDED Decimal (equity - pending). The Withdraw page 'Use max' posts available.toFixed(2). POST /investor/withdrawals recomputes available unrounded and refuses when amount > available, so whenever the raw figure rounded UP (e.g. equity 5120.506 -> shown 5120.51 > raw 5120.506) the maxed request is refused with 'amount exceeds what is available to withdraw (5120.51)' (the message itself is :.2f-rounded, so it displays the same figure it refused). Live equity can also move between the summary GET and the POST. Fix options noted in memory: round down server-side, or cap against the rounded value.
- No proof/receipt upload exists anywhere: deposit evidence is the investor-typed txid string (required, <=128 chars) plus optional note (<=500); withdrawal payment evidence is the admin-typed txid on /paid. There is no file storage, no image field, no screenshot column.
- QR code is rendered client-side from wallet.address via dynamic import('qrcode') in InvestorDeposit.tsx; the server stores only text.
- Deposit coin is forced to the wallet coin: POST /investor/deposits 400s unless coin.upper() == wallet.coin.upper(); the dashboard sends coin: wallet.coin. The org supports exactly ONE wallet/coin/network (PK org_id).
- One live txid per org: UNIQUE (org_id, txid) WHERE status <> 'rejected' — a rejected notice can be re-filed with the same txid; a confirmed or pending one cannot (409, even across investors).
- Rate limit 10 per hour per investor for deposit notices and for withdrawal requests, separate keys, in-process LoginRateLimiter (not shared across api workers/restarts).
- Rejections REQUIRE a note (clean_text required=(new_status=='rejected')); confirm/approve note optional. Decision status is .strip().lower()'d.
- Withdrawals need a linked account (409 'no account linked yet'); deposits do not. Deposits' account_id is filled at confirmation time from the link at that moment; summary sums by user_id never by account.
- Withdrawal with unknown equity (available None) is ACCEPTED, not refused; equity_verified=false and admin is expected to check the terminal. 'last known' equity caps the request but is never verified.
- Withdrawal rows carry no coin/currency; the dashboard labels them with the wallet coin, else 'USD'. API money fields are bare floats.
- Link semantics: PUT investors/{user_id}/account always unlinks first, then links; the target must be in this org, not role 'master', and not already linked to another investor (partial unique index + IS NULL guard). Dashboard hides master accounts and already-linked ones from the Select.
- investor_withdrawals.account_id is ON DELETE RESTRICT: an account with withdrawal history cannot be deleted.
- Role 'investor' ranks below 'viewer': every require_org_role('viewer'/'admin') endpoint and the org websocket (4403) refuse it; the investor router's handlers never accept an account id from the request.
- MPIN (migration 021) is only a login second factor; there is no per-action PIN check on any investor or admin money endpoint. Forgot MPIN needs only the password.
- Emails to investors are best-effort via broadcaster.alerter.send_to; a failed send never fails the request. Admin alerts fire only for the three warning actions.
- Deposit amounts are validated by parse_amount (<=2 decimals) but are NOT checked against anything on-chain; confirmation is purely the admin's judgement.
- Performance/success fees are an explicit non-goal in the spec (would be deducted at withdrawal time).
- Deploy note (memory): compose build api/copier alone skips new db/migrations; stop api before migrate.

### Reuse for the portal

- Wallets: org_investor_wallets is a single receiving-address card per org (one coin/network). A multi-wallet or per-investor balance ledger does not exist; portal 'wallet balance' today is equity (from the copier) minus pending withdrawals, not a stored balance. Reuse summarise()/summary_json for the figures; a stored per-user wallet balance would need a new table.
- Deposits: investor_deposits + POST/GET /investor/deposits and the admin decision endpoint are reusable as-is for a 'submit -> admin confirm/reject' flow. Missing for a broker-style portal: proof/receipt file upload (no column, no storage), multiple payment methods/coins (coin must equal the one wallet coin), fiat methods, and a status beyond pending/confirmed/rejected.
- Withdrawals: investor_withdrawals with requested -> approved -> paid (+ rejected) and the three admin endpoints map directly onto submit -> admin decision -> paid. Reusable including equity_at_request/equity_verified audit fields and email notifications. Would need: rounding fix for 'Use max' (round available down, or compare against the rounded figure), a coin/method field, and a fee field if fees are charged.
- Transfers (internal, between accounts/wallets): nothing exists; the ledger has no transfer table and no notion of moving between two accounts. Would be a new table + endpoints, ideally reusing parse_amount/clean_text/can_transition and the events audit pattern.
- KYC: nothing exists (users table has no document/verification columns; no upload storage). New tables + storage would be required; can reuse the admin decision pattern (Decision {status, note}, note required on rejection) and pc.notify emails (now also an in-app notification, gated by the recipient's per-topic prefs).
- PIN-gated actions: MPIN infrastructure exists at login only (users.mpin_hash, mpin_failed_attempts, mpin_locked_until, and the dashboard PinInput on Mpin.tsx). A per-action PIN check on withdraw/transfer would need a new dependency that verifies the MPIN inside the request and reuses the existing hash/lockout columns.
- Manager marketplace: the closest primitive is the account link (accounts.investor_user_id, PUT /investors/{user_id}/account, master-account guard). There is one master per org; investors are linked to follower accounts by the admin. A self-serve marketplace (investor picks a manager/strategy) has no data model; the link endpoint and the one-account-per-investor unique index would have to be relaxed or wrapped.
- Tickets: migration 025 (client portal phase 4) added ticket_subjects, tickets and ticket_messages; routes/portal_support.py gives the investor side (GET investor/ticket-subjects, POST/GET investor/tickets, POST investor/tickets/{id}/messages, POST investor/tickets/{id}/close) and the desk side (GET/POST tickets, tickets/{id}/messages, tickets/{id}/close; CRUD ticket-subjects), built on the events(category='control') audit pattern and a 10/hour LoginRateLimiter.
- Notifications: migration 025 (client portal phase 4) added notifications (one row per recipient per event; topic in money|identity|support|bonus; read_at) and notification_prefs (per-topic email switches); routes/portal_notifications.py gives GET notifications (cursor-paginated), GET notifications/unread-count, POST notifications/{id}/read, POST notifications/read-all, GET/PUT notification-prefs, and GET/PUT me/settings (theme). portal_common.notify()/notify_admins() write the in-app row then email via alerter.send_to unless the recipient's per-topic switch is off -- the replacement for the old _notify_investor.
- Bonuses: migration 025 (client portal phase 4) added bonus_rules (one row per org: signup/kyc/deposit switches and amounts) and bonuses (one row per payment; unique per user+source for signup/kyc, per deposit for deposit); routes/portal_bonus.py gives GET/PUT bonus-rules and POST investors/{user_id}/bonuses (admin), GET investor/bonuses (investor). Bonuses are paid into the Credit wallet and can only move on to a trading account (portal_ledger.TRANSFER_PAIRS).
- Frontend: InvestorOverview/Deposit/Withdraw/History/Account pages, investorNav, statusLabel/statusTone/pillClass, Timeline component pattern (requested/approved/paid), ConfirmDialog review step, Investors.tsx admin queues with Select link and Mark paid dialog are all reusable building blocks; types live in dashboard/src/lib/types.ts.
- Money contract to preserve: amounts as strings from forms, <=2 decimals, positive; all API money fields are floats rounded to cents; no currency field is emitted, so any multi-currency portal must add one to summary and rows.

### Constraints

- File naming: db/migrations/NNN_snake_name.sql, three-digit zero-padded prefix; runner sorts by full filename string (sorted(glob('*.sql'))). Two files share prefix 005: 005_multi_org.sql applies before 005_risk_snapshots_symbol.sql (lexical 'm' < 'r'). Next number is 022.
- Applied once each: db/migrate.py records each filename in schema_migrations and skips recorded ones. Migrations are NOT required to be idempotent (none use IF NOT EXISTS except the runner's own table), and renaming an already-applied file would re-run it.
- All pending migrations run in a single psycopg connection with commit only at the end: a failure in any pending file rolls back every pending file in that run. Each file is executed as one conn.execute(text) so multi-statement SQL and DO $$ blocks are fine.
- Deploy gotcha (memory note): `docker compose build api` / `copier` alone does not rebuild the migrate image, so new migration files are silently skipped; rebuild/run the migrate service (stop api first), then hard-reload the dashboard.
- Role CHECK constraints are named org_memberships_role_check and org_invites_role_check and have been dropped/re-added three times (005, 019, 020); any new role must repeat the DROP CONSTRAINT / ADD CONSTRAINT pair on both tables. Current values: admin, viewer, investor. Invites cannot carry a role outside that set.
- events.category CHECK is named events_category_check and is likewise replaced by DROP/ADD whenever a category is added (005_risk, 007_reminder).
- Tenant-history tables deliberately carry org_id WITHOUT a foreign key and nullable (events, portfolio_snapshots, executions, positions, deals, balance_samples) so history survives org/account deletion; tenant-config tables use FK orgs(id) ON DELETE CASCADE.
- accounts.ctid_trader_account_id is the universal account key even for MT5 (synthetic ids from mt5_account_id_seq starting 1000000000000); accounts_platform_link CHECK ties platform to presence of ctid_connection_id.
- Exactly one master per org: partial unique index accounts_single_master ON accounts (org_id) WHERE role='master'. An account has at most one owner; since migration 024 (client portal phase 3) an investor may own several, tracked by the non-unique accounts_by_investor index and capped by portal_settings.max_live_accounts (default 5).
- Every UPDATE on orgs bumps settings_version via trigger; writers doing compare-and-set must read it back.
- executions and balance_samples are range-partitioned by ts with monthly partitions created 12 months ahead at migration time and maintained by the copier (main.ensure_partitions); a DEFAULT partition catches overflow. Attaching a new monthly partition overlapping rows already in the DEFAULT partition takes a strong lock.
- Secrets are stored hashed only (org_invites.token_hash, org_webhooks.secret_hash, mt5_links.key_hash all sha256 hex; users.password_hash and mpin_hash argon2). No plaintext secret columns exist.
- investor_withdrawals.account_id is ON DELETE RESTRICT: an account with withdrawal history cannot be deleted; investor_deposits.account_id is SET NULL instead.
- settings table is a single-row (id BOOLEAN PK DEFAULT TRUE CHECK (id)) process-config table now holding only shards; per-org copying_enabled/dry_run live on orgs.
- Postgres container publishes 127.0.0.1:5433; the DSN inside compose uses host postgres:5432, user/db copytrader; local tests should use 127.0.0.1 not localhost (IPv6 hang).

### Reuse for the portal

- Identity/auth: users (email, password_hash, display_name, session_version, mpin_* columns) already provides email+password plus a 6-digit MPIN second factor with lockout state (mpin_failed_attempts, mpin_locked_until) -- PIN-gated actions can reuse mpin_hash verification as-is; nothing per-action exists yet.
- Tenancy: orgs + org_memberships with roles admin|viewer|investor; the 'investor' role is the client-portal role. Adding a new role requires re-creating org_memberships_role_check and org_invites_role_check.
- Client<->account link: accounts.investor_user_id is the mapping from a portal user to a trading account. Since migration 024 (client portal phase 3) the per-org uniqueness constraint was dropped (index accounts_by_investor is non-unique), so an investor may own several accounts, capped by portal_settings.max_live_accounts (default 5) and enforced in portal_common.link_account; an account still has at most one owner. The admin links/unlinks one at a time via POST/DELETE /investors/{user_id}/accounts.
- Deposits: investor_deposits (pending|confirmed|rejected, txid-unique-while-live, decided_by/decided_at/decision_note) is a crypto deposit-notice queue; extend for other payment methods by adding columns (method, network, reference) or a sibling table. No fiat/gateway columns exist.
- Withdrawals: investor_withdrawals (requested|approved|paid|rejected, destination, equity_at_request, equity_verified, paid_by/paid_at/txid) is a complete admin-approved cash-out queue reusable as-is; PIN gating would be enforced in the API, no column needed.
- Receiving wallet: org_investor_wallets is one wallet per org (coin, network, address, memo); a multi-wallet/multi-coin portal needs a new table keyed (org_id, coin, network) or a serial id.
- Balances/equity for wallet views: portfolio_snapshots (daily close), balance_samples (5-min series), mt5_links.balance/equity and the copier's live state can feed a client 'wallet' balance; there is no ledger/wallet-balance table -- balances are derived by summing confirmed deposits minus withdrawals per user_id.
- Transfers, KYC, manager marketplace, tickets, notifications: NO tables exist. New tables would follow the existing pattern: BIGSERIAL id, org_id FK orgs ON DELETE CASCADE, user_id FK users, TEXT status with CHECK, decided_by/decided_at/decision_note audit trio, created_at DEFAULT now(), and a (org_id, status, created_at) queue index.
- Audit/notifications: events (category CHECK, severity, payload JSONB, actor_email, org_id, account_id) with the pg_notify('events') trigger is the existing in-app feed/audit log; a client notification feed could add a category (requires replacing events_category_check) or a dedicated notifications table keyed by user_id.
- Invites/onboarding: org_invites (sha256 token_hash, role, expires_at, consumed_at/consumed_by) already supports inviting an investor by link; registration is otherwise gated by an api flag (see memory: registration closed in prod).
- Trading views for a client: positions, deals (with label), executions, mappings (symbol, fill_price, master_fill_price) scoped by account_id/org_id give the per-account history a client dashboard needs; the master/slave model (one master per org, accounts.multiplier) is the 'follow a manager' primitive, but there is no marketplace/strategy-listing table.

### Constraints

- Per-row action buttons must carry unique aria-labels (`Confirm deposit ${d.id}`, `Approve withdrawal ${w.id}`, `Mark withdrawal ${w.id} paid`, `Reject deposit ${d.id}`); Investors.test.tsx finds them by that exact name and then clicks the dialog's generic 'Confirm'/'Reject'/'Mark paid' button.

- Investors refresh() runs every POLL_MS=10000 and on live events; a form that the poll must not clobber needs a dirty ref (walletDirtyRef pattern) because refresh is memoized per orgId.
- The investor-wallet GET 404 is expected ('No wallet configured') and is swallowed via err.message.startsWith('404'); other errors surface in the Banner.
- Until the first load lands, pages show <Loading label=...> not an empty table (`loaded` flag); an error before first load shows only the Banner.
- All investor admin endpoints are require_org_role('admin'); UI hides controls with can(role,'control') but the server enforces. Investor role ranks -1 so it is refused by every viewer+ route.
- Investor decision endpoints already write a category 'control' event, which useLiveRefresh treats as a refetch trigger (250ms + 2000ms burst); Automation.test.tsx asserts this contract for webhook_alert.
- Logs.tsx must ignore socket frames without id/ts (the quotes relay); DeskStrip polls events?category=risk and category=reminder and dedupes banners by event id.

## MirrorFleet trading-account model: accounts table (cTrader + MT5), org scoping, roles, connection state, investor linkage, and the copier-backed analytics/history/positions read endpoints

One `accounts` table holds both platforms, keyed by `ctid_trader_account_id` (real cTrader id, or a synthetic id from `mt5_account_id_seq` starting 1e12 for MT5). `platform` ('ctrader'|'mt5') decides the connection door: cTrader rows point at `ctid_connections` (OAuth grant, status active|invalid|refresh_failed); MT5 rows have a `mt5_links` row holding the sha256 of a per-account key plus terminal-reported broker/login/balance/equity. Roles are `master|slave|ignored` with exactly one master per org (partial unique index on `org_id`). Every account is `org_id`-scoped; an investor is linked by `accounts.investor_user_id` (master never linkable; since migration 024, client portal phase 3, an investor may own several accounts, up to `portal_settings.max_live_accounts`, default 5 -- an account still has at most one owner). Live balance/equity/positions come from the copier `/state` (in-memory, no DB column); closed-trade stats come from the copier `/analytics` over the stored `deals` table; deal/order/cashflow history is proxied per week window.

### Constraints

- accounts has NO balance/equity column. Live equity is only in the copier's in-memory /state (null until the first balance refresh); MT5 last-known balance/equity live on mt5_links (updated at most every 10 s). Historical series: balance_samples (5-min), portfolio_snapshots (daily close). Dashboard shows a dash, never 0.00, when the engine has no reading.
- Exactly one master per org (accounts_single_master partial unique index). PATCH role='master' demotes ALL other non-slave accounts (including 'ignored') to 'slave' inside one transaction. The master cannot be linked to an investor (400) and an MT5 master cannot be removed (400).
- Role rank: investor(-1) < viewer(0) < admin(1). Every viewer endpoint refuses investors; investor endpoints (`require_org_role('investor')`) are open to any member but a desk member has no linked account and gets 'unlinked'. All dashboard actions trade/control/manage_members require admin.
- require_account_in_org must be called before proxying any account-taking read to the copier: the copier's own query routes are account-scoped with no notion of orgs.
- History endpoints require from/to epoch ms; cTrader rejects windows longer than one week and caps DealList at DEAL_LIST_MAX_ROWS=500 -> dashboard pages by week and reads has_more.
- /analytics weeks clamped to [1,12] in the api (MIN/MAX_ANALYTICS_WEEKS) and [1,26] in the copier; weeks=0 (all history) is only reachable by calling the copier directly. `truncated: true` means backfill has not covered the window, not paging truncation. Analytics reads the stored `deals` table (ANALYTICS_ROW_LIMIT bounded), so a fresh deployment shows near-empty stats until deal_backfill_state.exhausted.
- net_pnl semantics: sum of closing deals' gross_profit + swap, plus EVERY deal's commission (open and close legs charged separately). win/loss decided on close.gross_profit sign; zero-profit closes count in closed_trades but neither wins nor losses.
- Equity curve points are balance-after-close per closing deal (execution_timestamp, close.balance); weekly buckets start Monday UTC (_MONDAY_SHIFT_MS).
- MT5 connection_status: 'connected' if mt5_links.last_seen_at within MT5_OFFLINE_AFTER_S=15 s, 'offline' if a last_seen_at exists, 'never' otherwise. cTrader connection_status is ctid_connections.status; needsRegrant() = cTrader and status != 'active'.
- MT5 key: 'mt5_' + token_urlsafe(32), returned exactly once by create/rotate; only sha256 stored; must never appear in URLs or logs (scrub_secrets). Rotation invalidates the old key immediately (per-request lookup).
- MT5 accounts are created as disabled slaves with trader_login=0 and is_live=false; login/broker/currency arrive on first hello. Deleting an MT5 account cascades mt5_links, mt5_commands, symbol_cache, symbol_aliases, mappings; but investor_withdrawals.account_id is ON DELETE RESTRICT, so an account with withdrawal history cannot be deleted.
- Investor ledger: only 'confirmed' deposits and 'paid' withdrawals are money that moved; 'requested'/'approved' withdrawals are spoken-for (pending_withdrawn). profit = equity - net_deposits; available = equity - pending_withdrawn; both null when equity unknown. Withdrawal amount > available -> 400. equity_verified=true only when the copier answered live (not MT5 'last known').
- Transitions: deposits pending -> confirmed|rejected; withdrawals requested -> approved|rejected, approved -> paid|rejected. A rejection note is required. Unique live txid per org (rejected rows excluded).
- Investor rate limit: 10 deposit notices and 10 withdrawal requests per investor per hour (LoginRateLimiter window 3600 s).
- Investor list computes equity from ONE /state round trip for the org (never per investor); a copier outage degrades to 'last known'/'unknown' rather than failing the page.
- PATCH account writes are audited into events (category 'control', payload.action 'account_changed') and trigger POST {copier}/reload for role/enabled/multiplier; the copier caches a routing snapshot so edits do not apply until reload.
- Money in DB is NUMERIC(18,2) for deals/positions/ledger but DOUBLE PRECISION on mt5_links.balance/equity; API responses cast to float. Volumes are protocol units (cTrader: lot_size per 1.00 lot; MT5: centilots, CENTILOTS) with volume_lots as a formatted string.
- dashboard orgApi(orgId, tail) builds /api/orgs/{orgId}/{tail}; every mutation carries X-CSRF-Token from the 'csrf' cookie; a 401 with detail 'MPIN required' routes to /mpin, other 401s to /login.
- Deploy note from memory: new db/migrations need the migrate image rebuilt (compose build api/copier alone skips them); stop api before migrate.

### Reuse for the portal

- Wallets: org_investor_wallets (one receiving address per org: coin, network, address, memo) + GET/PUT /investor-wallet and GET /investor/wallet are reusable as-is for a single-currency deposit address; a per-user or multi-coin wallet would need a new table keyed (org_id, user_id[, coin]) since the current one is org-singleton.
- Deposits: investor_deposits + POST/GET /investor/deposits (investor) and GET /investor-deposits, POST /investor-deposits/{id}/decision (admin) implement notice -> confirmed|rejected with duplicate-txid protection, hourly rate limit, audit events and investor email. Extending to fiat/other rails only needs new `coin` values and, if wanted, a `method` column.
- Withdrawals: investor_withdrawals + POST/GET /investor/withdrawals, admin decision and /paid endpoints already model requested -> approved -> paid|rejected with equity cap (equity_at_request, equity_verified) and txid on payout. A multi-step 'processing' state would add to WITHDRAWAL_TRANSITIONS in investor_ledger.py.
- Balance/equity/P&L for a follower performance page: GET /investor/summary (equity, net_deposits, profit, available, equity_source) plus GET /investor/analytics?weeks (closed_trades, wins, losses, win_rate, profit_factor, net_pnl, max_drawdown, equity_curve, per_symbol, weekly) and GET /investor/positions (open positions with pnl_quote). The desk equivalents are /accounts/{id}/analytics and /state. Both already return the exact 'stat tile' numbers; a portal would only need charts.
- Manager statistics page: today there is no manager entity. The master account per org is the strategy; its numbers are GET /accounts/{master_id}/analytics (viewer) and /state.master_positions, but investors (rank -1) cannot call those. A marketplace would need either a new investor-visible endpoint exposing the org master's analytics (proxying the same copier /analytics with the master's account_id resolved server-side) or a materialised stats table filled from `deals`/`balance_samples`.
- Trade lists: /investor/history/deals|orders|cashflow (from/to ms, weekly windows, has_more) give closed-trade rows with close.gross_profit/swap/commission and balance-after; the `deals` table (account_id, execution_timestamp DESC index) can back a DB-side paginated trade list without broker round trips. positions table (status open|closed, realized_pnl) exists but no api route reads it yet.
- Transfers between accounts: nothing exists. The ledger is per (org_id, user_id) with an optional account_id; an internal transfer would be a new table plus two ledger rows, and the summarise() rule set would need a 'transfer' kind.
- Investor -> account linkage: accounts.investor_user_id, now a one-(investor)-to-many link since migration 024 (client portal phase 3) dropped accounts_one_per_investor in favour of the non-unique accounts_by_investor index and a portal_settings.max_live_accounts cap (default 5); the admin links/unlinks one account at a time via POST/DELETE /investors/{user_id}/accounts (any non-master account, MT5 or cTrader). An account still has at most one owner. A follower who copies several *managers* (as opposed to owning several of their own accounts) would still need a separate many-to-many model.
- KYC: nothing exists; users has only email/password_hash/display_name. The events table (category 'control', severity 'warning' alerting admins) and the deposit decision pattern (status + decided_by/decided_at/decision_note) are the reusable shape for a kyc_submissions table and admin review queue.
- PIN-gated actions: the MPIN second factor exists at login (migration 021, routes/mpin.py, /api/me/mpin, api.ts routing 'MPIN required' -> /mpin). It is a session gate, not a per-action gate; a step-up check on withdraw/transfer would reuse the same verify code path from routes/mpin.py but needs a new per-request verification (e.g. an X-MPIN header or a short-lived step-up token).
- Manager marketplace: org = desk = one master; the platform_by_account/role model supports one strategy per org. Listing 'managers' across orgs needs a cross-org public read (today every route is org-scoped by path and membership).
- Tickets / notifications: migration 025 (client portal phase 4) added tickets/ticket_messages/ticket_subjects and notifications/notification_prefs tables (routes/portal_support.py, routes/portal_notifications.py), written by portal_common.notify()/notify_admins() -- see the investor money model section's Reuse notes above for the table and route list; that replaces the old _notify_investor helper.
- Account cards: _account_card() in investor.py ({account_id, nickname, platform, status, last_error, connected}) and the AccountRow/AccountDrawer components (connectionHealth, mt5Subtitle, accountRoleLabel 'Follower') are directly reusable for a portal 'my trading account' panel.
- Connection state and platform badges: isMt5(), accountName(), accountIdent(), connection_status semantics (connected|offline|never vs active|invalid|refresh_failed) are ready for any portal list; MT5 onboarding (POST mt5/accounts -> key + install steps, KeyRevealDialog) could be exposed to investors if the role gate (admin) is relaxed to a new self-service endpoint.

## Build, test and deploy conventions (docker-compose, api image, migrations, notifications, commit rules)

Four compose services: postgres:16 (loopback 127.0.0.1:5433), a one-shot `migrate` job (db/Dockerfile, runs `python -m db.migrate`, applies db/migrations/*.sql in filename order once each, recorded in `schema_migrations`), `copier`, and `api` (FastAPI/uvicorn on 127.0.0.1:8000). The api Dockerfile is a two-stage build: node:22-slim runs `npm ci && npm run build` on dashboard/, then python:3.12-slim copies `/dash/dist` to `/app/static` (plus mt5/MirrorFleet.mq5 under static/downloads) and main.py serves it with an SPA fallback when STATIC_DIR is set. API tests are pytest against a real Postgres scratch DB `copytrader_test`; dashboard tests are palette prover + tsc + vitest. No object storage, no SMTP: email is Resend HTTP API, Telegram is Bot API, both instance-wide and event-driven via ws.py's EventBroadcaster.

### Contracts

- API tests (Windows, local venv, Git Bash from api/, Docker Desktop running and `docker compose up -d postgres` first): `export TEST_POSTGRES_ADMIN_DSN="postgresql://copytrader:${POSTGRES_PASSWORD}@127.0.0.1:5433/copytrader"; export TEST_POSTGRES_DSN="postgresql://copytrader:${POSTGRES_PASSWORD}@127.0.0.1:5433/copytrader_test"; export PYTHONPATH="$(pwd -W)/src"; .venv/Scripts/python -m pytest tests -q -p no:cacheprovider` (POSTGRES_PASSWORD from repo-root .env).
- API tests (Linux container, full suite incl. test_events_ws.py), Bash tool from repo root: `export MSYS_NO_PATHCONV=1 && docker compose run --rm -v "$(pwd -W):/repo" -w /repo/api --entrypoint sh api -c 'export PYTHONUSERBASE=/tmp/pyuser; pip install -q --user "pytest>=8" "pytest-timeout>=2" "pytest-asyncio>=0.24" "websockets>=12" >/dev/null 2>&1; export PYTHONPATH=/repo/api/src TEST_POSTGRES_ADMIN_DSN="$POSTGRES_DSN" TEST_POSTGRES_DSN="${POSTGRES_DSN%/copytrader}/copytrader_test"; python -m pytest tests -q -p no:cacheprovider'` (~8-14 min).

### Constraints

- `docker compose build api copier` does NOT rebuild the migrate image; a deploy touching db/migrations/ must `build migrate` and `run --rm migrate` or the migration is silently skipped ('applied: nothing (up to date)').
- Stop the api container before running migrate when a migration tightens a constraint or changes values the running api writes; hard-reload dashboard tabs after `up -d api` (stale bundle; ChunkBoundary reloads once per ten seconds).
- On Windows use 127.0.0.1 not localhost in the test DSNs (localhost resolves IPv6 first and psycopg hangs until pytest-timeout); set PYTHONPATH to src so the edited source runs; Git Bash needs MSYS_NO_PATHCONV=1 for docker -v mounts; PowerShell 5.1 strips embedded quotes in native-exe args.
- Pre-existing Windows-only api failures: 7 tests in test_events_ws.py error (psycopg async on ProactorEventLoop) and one EA-download test fails on CRLF; both pass in the Linux container -- do not fix.
- api and copier suites share copytrader_test: never run them concurrently. e2e must run as its own compose project (`-p tbe2e`) or `down -v` deletes the dev pgdata volume.
- The api container runs as unprivileged uid 10001, writes nothing to disk, and has no volume mount; STATIC_DIR is baked read-only content. Any file-upload facility would need a new bind/named volume on the api service (or external object storage) plus a new python-multipart dependency -- none exists today.
- No SMTP anywhere: all email goes through the Resend HTTP API with a single instance-wide recipient (ALERT_EMAIL_TO); per-investor mail uses EmailAlerter.send_to and needs only RESEND_API_KEY. Leaving RESEND_API_KEY/ALERT_EMAIL_TO empty makes the alerter inert (enabled=False).
- Telegram is instance-wide (one bot, one chat); reminders are deliberately not emailed; both notifiers are event-driven (a row INSERTed into `events` with matching category/severity/payload.action is the way to trigger them) and rate-limited 15 min per (action, scope).
- REGISTRATION_ENABLED defaults false in production (host .env currently false; only mirrorfleet@gmail.com exists); tests set it true because users are created via POST /api/register.
- ApiConfig.from_env raises ValueError when SESSION_SECRET, FERNET_KEY or any CTRADER_* var is empty -- new env vars should follow the `os.environ.get(NAME, default)` pattern with a documented line in .env.example.
- Dashboard `npm test` fails on any WCAG pair in palette_check.mjs across both themes; colours must be --color-* tokens in src/index.css; use design-system primitives (Button, Input, Select, Badge, Drawer, Banner, Card, Tabs, PageHeader) rather than hand-written class recipes; glass only on floating chrome; vocabulary test forbids 'Slave' in UI strings (use 'follower').
- Never touch copier/ for portal work (plan convention); API-untouched gates are proven with grep in Task 10 of the redesign plan.
- CLAUDE.md does not exist; conventions live in README.md, docs/superpowers/plans/*.md 'Global Constraints' sections and the user's memory notes.
- Deploys happen only on the user's explicit say-so; work on branch (currently client-portal) and finish via superpowers:finishing-a-development-branch.

### Reuse for the portal

- Migration pipeline as-is: add db/migrations/022_<name>.sql (next number after 021_mpin.sql), a matching api/tests/test_migration_022.py asserting order and column shape, and add every new table to conftest's `db` TRUNCATE list.
- Test fixtures as-is: make_user/make_org/login_as/org_client and the investor test helpers (_member, _link, _wallet, _state) in api/tests/test_investor_portal.py already model an investor role with wallets, deposits and withdrawals -- extend the same file pattern for transfers, KYC, tickets.
- PIN-gated actions: the MPIN gate already exists (session cookie key `pin`, routes /api/mpin/set|verify|reset, /api/me/mpin, require_half_session vs require_user); a per-action re-verify would reuse api/src/api/routes/mpin.py's verify/lock logic (5 tries, 15 min lock, 401 'Invalid MPIN' with attempts_left, 423 'MPIN locked').
- Notifications: add new (category, severity, action) tuples to ALERT_RULES (with a subject prefix) and TELEGRAM_RULES; investor-scoped actions must start with 'investor_' and carry payload.user_id so the cooldown scopes per investor; emitting means INSERTing into `events`, the broadcaster does the rest. Per-user email uses EmailAlerter.send_to(to_addr, subject, text) (see routes/investor.py:152).
- Email infra to extend: Resend only, instance-wide FROM/TO; a multi-recipient or templated portal mail (ticket replies, KYC decisions) would add new send_to calls, not new transport. No SMTP config exists and none should be assumed.
- Uploads (KYC documents, deposit proofs): nothing exists -- no UploadFile/multipart routes, no S3/MinIO, api container writes nothing to disk and has no volume. Would require either a named volume mounted on the api service (and a STATIC-like served path with auth) or an external object store, plus python-multipart in pyproject and backup coverage in ops/backup.sh (which today dumps only Postgres).
- Dashboard: tests follow the vi.mock('../../lib/org') + mockUseOrg(role) pattern from dashboard/src/test/orgMock.tsx; new pages must pass palette_check, tsc and vitest via `npm test`; investor pages live under dashboard/src/pages/investor/.
- Deploy: no change needed -- the api image builds the dashboard, so portal pages ship with `docker compose build api`; with a migration follow the build migrate api / stop api / run --rm migrate / up -d api sequence.
